## 已知限度

- 本机 Windows 应用控制阻止 pyarrow DLL，系统环境无法运行 TRL / datasets；训练、survey、评测均在集群执行。本机另建的临时虚拟环境可跑 `--tiny` 与依赖 torch 的单元测试。
- 被拒组仍计入 `grpo` 损失的逐序列均值分母，该步损失按保留比例缩小。
- 双卡 DDP 在本机只以 CPU / gloo 两进程跑过 `--tiny`（跨卡被拒组两卡都掩码、LoRA 两卡一致）；集群双卡 NCCL 尚未验证。

## 变更记录

- 2026-10-06：训练支持双卡 DDP（Accelerate，不用 DeepSpeed），单卡行为不变。全局批次保持每步 2 × 8，每卡 8 个；被拒组在整批上判定、两卡一致掩码，连续全拒计数跨卡同步；种子、裁判目录、API 预算、检查点奖励状态按卡分开并按卡续训；`verification.json` 实测两卡 LoRA 参数一致。此前单卡续训测试通过（桩裁判 12 步，第 5 步中断后续训）。

- 2026-10-05：中断防护。grpo_style_01 在第 10–12 批、grpo_style_03 在约第 45 步因连续 3 批全部组被拒中止（03 为 HTTP 429），且无检查点，进度全部丢失。裁判 API 对超时、断连、408 / 429 / 5xx 退避重试（15–240 s，约 8 分钟，计入预算）；训练每 10 步存检查点（含奖励计数），`--resume` 从最近的完整检查点继续，并核对与原 manifest 一致。首次续训测试（grpo_stub_resume_01）在加载优化器状态时被 transformers 的 torch < 2.6 检查拦下；改为保存时记录检查点文件哈希，核对一致后才放行。
- 2026-10-04：裁判协议 `style-v3`。survey_style_03（`style-v2`）门槛通过：被拒组 0/20（5 次调用经重试成功，无残留失败）、有差异组 0.90、胜率 0.452；但 AB/BA 不一致率 0.248，而 survey_style_02 是 0.151，两次 160 条策略回复逐条相同。两次之间 23 个样本由一致变不一致，9 个反向（McNemar p≈0.01）；Rei 6→11 / 68，明日香 15→25，两角色都升，不是“本小姐”那句造成的；不一致与一致样本的字面相似度 0.47 / 0.46，也不是措辞相近造成的。归因于键序：`winner` 先于任何分析。`style-v3` 改为先写逐句对比、再下结论，`scores` 仍在最后。
- 2026-10-04：`style-pairwise-v3`，裁判协议 `style-v2`。survey_style_02（v2 规则）门槛未过：20 组拒 5 组（0.25 > 0.2），其余指标在范围内（有差异组 0.87、胜率 0.446、顺序不一致率 0.151、硬违规 0）。5 组都因解析失败，268 次调用中 7 次，全是同一种：裁判少写一个右花括号，`reason` 与 `preference_evidence_ids` 落进 `scores`。改为让 `scores` 最后输出；奖励侧调用 / 解析失败重试 1 次。另外裁判的 P 理由普遍以“使用本小姐”为加分证据，基座开头比例仍为 0.925，提示中补一句“出现本身不是加分理由”。改提示即改裁判，v2 下的 survey 结果不与 v3 混用。
- 2026-10-04：`style-pairwise-v2`。survey_style_01（v1 规则）20 组拒 13 组，全部因 AB/BA 不一致；门槛却显示通过，因为它只看可用组。逐样本 145 个比较中 27 个不一致：15 个两种顺序都选前一个（位置偏差），12 个一次判平一次分胜负，22 个出自明日香措辞相近的同义改写。改为不一致记平局并记录不一致率；门槛增加被拒组 ≤ 20%。同时从明日香语气词中删去“本小姐”（基座 97% 的回复以它开头），改为单列指标。按 v2 规则，这 13 组都不会被拒；v2 下的 survey 另行重跑。
