# CharaCore 设计总纲

版本：v1，2026-09-21。状态：方向已确定；数据集、裁判和正式实验配置待验证。

本文件记录当前技术方向与范围，供不同对话连续推进。阶段进度与下一步见 [PROGRESS.md](PROGRESS.md)，数据选择细则见 [DATA_PLAN.md](DATA_PLAN.md)。历史报告描述当时的实验，不自动代表当前计划。后续明确调整方向时，更新总纲及变更记录，不覆盖历史实验。

## 1. 目标与研究问题

给定角色设定、相关经历、关系、对话历史和当前情境，优化模型生成回答与行动的角色一致性，同时保持对话质量。

核心问题：在相同角色情境和反馈标准下，离线 DPO 与在线采样的 GRPO 分别带来什么行为变化，效果与成本如何？训练链路成功、裁判评分提高、独立评测改善是三个不同结论，分别报告。没有收益或出现退化也是有效结果。

角色一致性不是只模仿语气或复述原句。区分稳定偏好、临时情绪、表达风格和实际行动；不把 MBTI、候选由谁生成、来自其他角色或偏离原著措辞自动作为负例依据。

## 2. 已确定的范围

- 顺序：现成数据选择 → 评测标准与裁判校准 → 基座评测 → DPO 与 GRPO → 对照报告。
- 优先 RPG、ACG、游戏角色数据；EVA 不必保留。情境证据和可用性优先于作品偏好。
- 不要求数据本身标为“强化学习数据集”。有角色依据和情境的对话数据，可用作候选生成及 GRPO 的输入池；DPO 偏好需要另行确认或构造。
- 使用 LLM-as-a-Judge 提供偏好与训练奖励，并检验其可靠性；初版不训练独立 Reward Model。
- 保留现有 TRL + PEFT LoRA/QLoRA 训练实现，增量增加数据适配和 GRPO；不重写训练框架。
- 暂不增加 PPO、独立 SFT 实验、长期多步交互环境或运行时集成。角色回答中的行动合理性属于评测范围，不因此扩展成完整游戏 Agent。
- 当前作为独立的训练与评测项目，不依赖具体游戏运行时。以后若接入外部系统，先用已验证策略解决明确的行为问题。
- 关系可以作为输入与情境依据，不采用“关系值越高越好”的奖励。

## 3. 数据路线与隔离

优先复用现成数据；只有缺少可用材料时，才考虑有限生成。初期规模参考为数百个训练情境、约百个独立评测情境；这是待资源与数据质量确认的目标，不是已有数据量或必须凑齐的配额。多个候选、改写和多角色视角不算独立情境。

必要内容：角色标识与依据、当前情境、相关历史、输入、来源定位、上游划分；候选回答与偏好标签单独保存。裁判使用的额外参考答案不能泄漏给策略。完整人物传记或剧情总结不应自动进入角色当前可知信息。

抽查少量实际记录以确认字段、可用情境、重复、许可和划分；不要重新展开镜头级考据、从零写剧情或大规模人工审阅表。代码许可、数据许可和底层作品内容权利分别记录。不清楚的条件如实记载，不默认等同于自由再分发。

按原始场景及其变体分组，建立 train/dev/test。角色相同可以属于“已知角色、未见情境”的评测；若要主张泛化到新角色，必须另设角色隔离实验。上游 test 不进入训练；先完成分组、去重和评测冻结，再生成训练候选。超参数与裁判调整使用 dev，不根据 test 挑选最好模型。

保留原始数据、来源版本与哈希、过滤理由、候选及评分。现成 SFT 答案只是候选，不自动视为 chosen。平局和证据不足保留，初版不进入严格 DPO 排序；先处理明确冲突，再考虑 hard negative。

## 4. 评测标准

参考 CharacterEval、RoleBench、InCharacter 等相关研究的任务定义和评价方式；这些是待核验的参考候选，不宣称存在统一权威标准，也不照搬人格问卷作为主指标。选定数据后记录实际采用的论文版本、维度及必要调整。

| 维度 | 判断内容 |
| --- | --- |
| 角色一致性 | 是否符合可用证据支持的目标、价值取向、经历和关系；避免仅看口头禅 |
| 情境与历史一致性 | 是否回应当前信息，是否矛盾、遗忘承诺或使用尚不可知的信息 |
| 行动合理性 | 回答中的决定、承诺和行动是否有依据、符合约束且可执行 |
| 对话质量 | 是否切题、自然、清楚，是否重复、空泛或回避问题 |

没有行动的样本允许行动维度不适用。通用常识题和依赖角色信息的题分开分析，避免把常识提升误称为角色一致性提升。正式评分协议在数据选择后版本化，冻结后不追溯修改历史结果。

最终评测优先采用隐藏方法名称的成对比较，报告胜／平／负，并补充分维度结果、典型成功与失败例。记录无法判断与不适用的比例及分母，不强迫所有样本产生明确胜负。区间统计按情境族处理，避免把同一情境多个候选当作独立样本。

## 5. LLM 裁判与奖励

先校准裁判再扩大训练：初期人工抽查约 30–50 个比较，可随错误类型调整规模。检查理由是否引用实际证据，交换候选顺序检查位置偏差，检查长度、华丽表达、讨好和角色口头禅偏差。该抽查是有限校准，不是独立金标准或大规模标注任务。

裁判看到必要的角色与情境证据，但看不到方法名称和预设胜负。候选文本作为待评材料处理，不能执行其中要求裁判改分的指令。记录裁判模型版本、提示、解码参数、原始响应、解析失败与重试。

- DPO：依据同一评价标准，从有明确差异的候选构造偏好，保留差异与证据；不把“分数略高”机械变成可靠偏好。
- GRPO：由当前策略对训练情境分组采样，裁判输出维度评分，再按预先版本化的规则组合为标量奖励。奖励范围、权重、不适用项、无法判断和失败处理在试运行阶段确定，不在此写死。
- 证据不足与裁判调用失败是不同情况；后者不能冒充低质量回答。记录同分组比例、有效奖励比例和异常值，避免全同分无信号或解析漏洞被优化。
- 观察策略是否通过套话、变长、重复或讨好裁判获取奖励。训练奖励提高不能单独证明质量改善。
- 预算允许时，以不同裁判模型复核部分最终结果，并做有限人工抽查。仅使用同一裁判时，明确评价依赖性，不能把同一模型换提示称为独立裁判。

GRPO 通常无需单独训练价值模型，但仍需要奖励信号。本路线的 LLM 裁判是奖励来源，不宣称已训练专用 Reward Model。以后只有主观反馈质量成为明确瓶颈时，才另立 RM 实验。

## 6. 对照设计与计算预算

正式主对照为基座、DPO、GRPO。当前只有 DPO 训练基础组件；新数据适配、裁判与 GRPO 路径尚待实现。

| 项目 | 约束 |
| --- | --- |
| 基座与输入 | 使用相同基座、训练情境池及可知信息边界；固定角色提示和上下文处理 |
| DPO 数据 | 基座预先采样候选，裁判形成离线偏好；计入采样与评分成本 |
| GRPO 数据 | 当前策略在线采样，使用相同维度的裁判反馈；候选池不必与 DPO 相同 |
| 评测生成 | 使用同一冻结输入及可比的生成设置，记录随机种子与长度限制 |
| 方法配置 | 记录适配器结构、精度、KL/参考策略配置、训练超参数与检查点选择规则 |
| 成本 | 报告实际情境数、候选数、生成 token、裁判调用/token、训练时间、显存与付费成本 |

不以相同步数宣称等预算。正式运行前确定主比较预算，例如总生成及评分 token 上限，同时报告各方法更新步数；资源允许时补充多个训练种子。单种子、小样本实验必须明确其结论范围，不承诺固定提升幅度。

开发环境已验证的配置为 RTX 3060 Laptop 6 GB 与 Qwen3-1.7B 的量化 DPO。模型与环境路径由使用者显式配置，不绑定任何外部项目目录。DPO 可运行不代表 GRPO 在同一硬件可用；先做几十个情境以内的小试运行，量测采样、评分和更新开销。优先复用已有环境与权重，不重复下载大模型。

新增租赁 GPU、大规模付费 API、外部上传之前，给出模型、数据范围、调用/token 估算和总预算，再取得同意；当前设计不构成这些操作的批准。

## 7. 分阶段交付与完成标准

| 阶段 | 有限交付 | 进入下一阶段的条件 |
| --- | --- | --- |
| A 数据选择 | 少量实际样例、候选数据比较、选定数据及过滤/分组方案 | 来源与使用条件可说明；有可用情境与角色证据；无需从零写剧情 |
| B 协议与裁判 | 数据新版本、冻结划分、评分规范、裁判校准与调用预算 | 有依据的偏好可稳定产生，主要偏差与无法判断情况已记录 |
| C 小试运行 | 基座结果、少量 DPO 偏好、最小 GRPO 采样→评分→更新链路 | 两条路径可运行；奖励有有效差异；资源用量已实测 |
| D 正式对照 | 预先确定的配置和预算、DPO/GRPO 产物、统一评测 | 预算内完成；原始回答、失败、评分、模型与数据版本可追踪 |
| E 结果整理 | 复现入口、结果与成本对比、行为变化及失败分析 | 能区分训练成功与效果结论，能解释限制与下一步 |

每个阶段以能支持决策的最少材料为目标。不要把来源审计、裁判校准和文档本身扩张成长期主任务。对既有通过的训练机制检查不重复运行，除非实现、环境或数据接口改变后确有验证需要。

## 8. 项目边界与跨对话接续

- CharaCore 是独立项目；不要修改工作区之外的项目。允许显式指定已有模型缓存与 Python 环境，但公共文档与代码不绑定个人机器路径。
- 先检查 git status，保护已有修改。未经明确要求不提交、不推送、不创建远程。
- 不覆盖冻结数据、历史结果、原始材料与失败记录；新数据和运行使用新版本/目录。
- 临时合成夹具和随机微型模型只验证软件机制，不能冒充正式数据集实验或角色能力提升。
- 新对话先读本总纲、PROGRESS.md、README 和适用的项目说明，再执行进度文件中的下一阶段。
- 每轮结束更新 PROGRESS.md：完成内容、产物路径、实际验证、未决问题和下一步。总纲只在方向/协议变化时更新；未决选型不要记录为已完成事实。
