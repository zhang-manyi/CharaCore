# CharaCore 设计总纲

更新：2026-09-22。当前状态见 [PROGRESS.md](PROGRESS.md)。本文件维护当前范围；数据审核与旧协议文档记录各自版本，不再分别维护项目路线。

## 目标与近期交付

研究角色回答与实际行动的一致性：模型能否根据角色依据、已知信息、任务状态和历史承诺做出合理决定，并通过工具执行。后续用经过校准的 LLM-as-a-Judge 提供偏好与奖励，比较基座、最小 GRPO 和已有 DPO 路径的行为与成本。

近期先完成一个可运行、可回放的单角色短任务。先观察基座行为和失败，再决定需要优化什么。离线环境开发、规则检查和基座轨迹采集不以完成三角色全池审核或裁判校准为前提；使用裁判给出可信评测结论或训练奖励则需要实际校准。

## 最小实现范围（待实现）

- 一个角色、一个有限任务环境。优先采用明确标为设计测试环境的任务和角色约束，不把自拟剧情当作原神原作，也不声称它验证了原作角色能力。
- 一个交互循环：读取可见观察和相关事件 → 模型输出回答或工具请求 → 校验参数与前置条件 → 执行 → 更新状态并记录结果。设最大步数和明确终止条件。
- 三类本地工具即可：查看可发现线索、查询任务状态、提交行动。工具实际读取或改变环境状态，模型说“完成”不代表任务完成；失败也返回可回放记录。
- 状态用显式字段保存任务进度、已知事实和承诺；记忆用带轮次的事件列表，只提供角色已经观察到的内容。
- 先提供 CLI 和 JSON 轨迹，能查看输入、回答、工具参数、执行结果、状态变化与失败。展示界面在闭环可运行后按需补充。

首版不建设通用 Agent 框架、独立 Planning/Reflection 服务、向量数据库、多 Agent、GUI/Browser 自动化或完整游戏运行时。只有实际失败暴露出明确需求时才增加模块。

## 验证顺序与完成条件

| 步骤 | 交付与条件 |
| --- | --- |
| 离线功能闭环 | 正常完成、非法行动、跨轮承诺的回放；脚本策略只验证环境机制，不能充作基座结果 |
| 基座运行与规则评测 | 接入显式配置的本地模型；报告任务完成、工具调用成功、非法状态转换、承诺保持的原始计数与失败轨迹；区分模型决策错误与环境拒绝后的安全状态 |
| 最小消融 | 同一任务集合比较有/无事件记忆或状态约束，每次只改一个因素；开发任务只支持开发诊断，不作为独立泛化证据 |
| 裁判评测与最小 GRPO | 小试输入有可追溯证据、可知边界和分组；真实人工/模型校准通过，奖励和失败处理可用，模型配置与资源预算明确后，打通采样→评分→更新 |
| DPO 对照与结果整理 | 复用已有训练器和可比输入/评测条件，报告行为变化、失败及实际成本；无需先完成大规模多角色实验 |

离线功能可以立即开发。本地基座运行还需确认模型路径、推理配置和资源可用；当前未运行。正式未见情境效果比较须有未参与开发的独立留出，不因演示缩小而取消隔离要求。设计任务的变体也须按任务来源分组，不把改名或换数值当作独立情境。

## 数据与证据

保留 ChatHaruhi 固定来源、现有开发材料和审核结果，详见 [数据审核报告](GENSHIN_STAGE_B_DATA_AUDIT.md)。它们用于来源研究与原神开发诊断，不要求继续整理完整池才能实现短任务环境。CoSER 保留为已考察的备选，当前不预先实现第二套适配器。

每个使用的情境只维护必要信息：来源与版本、事件分组、用途、当前可见输入、逐项角色依据；候选、标签和隐藏参考另存。稳定偏好、当前立场与情境事实分别标明适用范围，完整人物总结及后续剧情不能直接进入策略输入。

数据审核与开发调参暴露分别记录；已用于刺激或协议设计的来源及同事件变体不能进入盲测。文件数、候选数和截点数不代表独立情境数。现有 train/test 仍为 0/0，不设凑数量的配额。

## 评测与奖励

任务完成和工具执行首先按环境事实检查；角色一致性、情境与历史一致性、行动合理性、对话质量沿用已有四维协议。规则正确不等于角色表现可靠，训练更新成功也不等于效果改善。

现有 [v0.3 人工校准流程](GENSHIN_STAGE_B_CALIBRATION.md) 和36对刺激保留，暂不扩充。人工独立标注，锁定首轮后处理分歧，再揭示设计预期。助手预期不是人工金标准；解析检查不能证明引用真正支持理由。

当前裁判提供方和模型均未选定，外部调用禁用。真实调用时记录模型版本、提示、生成设置、原始响应、失败和成本；检查顺序交换及与人工判断的一致性。现有原神校准包不自动证明裁判能可靠评价新任务，迁移时只补实际需要的证据与适用性检查。

GRPO 奖励组合尚未验收。证据不足、同分和技术失败分别处理，不把缺失或失败补成零奖励。DPO 只使用有依据的严格偏好，保留 tie/insufficient。训练收益需在相同评测条件下比较；不以相同步数代表等成本，也不以同一裁判涨分代表全面能力提升。

## 复用现有实现

保留 TRL + PEFT LoRA/QLoRA DPO、无标签情境接口、离线裁判解析和校准包工具，不重写训练框架。现有6 GB设备只验证过 DPO；GRPO 的显存、吞吐和有效奖励率仍需小试实测。

已有 DPO --suite 接口保持不变：

| 文件 | 内容 |
| --- | --- |
| profiles.json | 角色 name、role、stable_preferences、style |
| train.json / eval.json | 训练与按情境族隔离的评测记录 |
| evaluation_plan.json / freeze.json | 评测计划及冻结文件哈希 |
| train_manifest.json | 训练数据与评测冻结版本的绑定 |

记录字段为 id、family、character、goal、relationship、history、emotion、situation、user、candidates（a/b）、preference、evidence。仅 a/b 进入严格 DPO；候选、标签与评分证据不进入策略提示。新环境轨迹无需伪装成此契约，训练接入时再做必要转换。

## 工作边界

- 当前离线阶段不调用外部 API、不上传、不租 GPU、不下载大模型、不启动正式训练；后续外部资源需另行明确授权。
- 保留原始缓存、旧快照、请求、结果与失败记录；新运行使用新目录。data/raw/、runs/、model_cache/ 保持 Git 忽略；不自动提交、推送或创建远程，不修改工作区外项目。
- 数据按来源许可管理；设计测试环境、软件机制验证、真实模型表现和人工标注分别报告。
- 只为实际实现变化做相应验证；不重复无关训练测试。每轮更新 PROGRESS，当前路线只在本文件维护。
