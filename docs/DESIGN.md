# CharaCore 设计总纲

更新：2026-09-23。当前状态见 [PROGRESS.md](PROGRESS.md)。本文件维护当前范围。

## 目标与近期交付

研究角色回答与实际行动的一致性：模型能否根据角色依据、已知信息、任务状态和历史承诺做出合理决定，并通过工具执行。主线用 LLM-as-a-Judge 的成对偏好作为奖励，通过 GRPO 优化策略在具体状态下的下一步动作。

主线聚焦**强化学习**：环境给出可验证的执行结果，裁判给出成对偏好，两者组合成奖励。奖励安全性优先于训练能否继续——证据不足、解析失败或调用失败都中止更新，不补零。裁判可靠性未测量时据实标注，不冒充校准通过。

## 实现范围

- 一个角色、一个有限任务环境，明确标为设计测试环境。不把自拟剧情当作任何已有作品的原作设定，也不声称它验证了原作角色能力。
- 一个交互循环：读取可见观察和相关事件 → 模型输出回答或工具请求 → 校验参数与前置条件 → 执行 → 更新状态并记录结果。设最大步数和明确终止条件。
- 三类本地工具即可：查看可发现线索、查询任务状态、提交行动。工具实际读取或改变环境状态，模型说“完成”不代表任务完成；失败也返回可回放记录。
- 状态用显式字段保存任务进度、已知事实和承诺；记忆用带轮次的事件列表，只提供角色已经观察到的内容。
- 先提供 CLI 和 JSON 轨迹，能查看输入、回答、工具参数、执行结果、状态变化与失败。展示界面在闭环可运行后按需补充。

首版不建设通用 Agent 框架、独立 Planning/Reflection 服务、向量数据库、多 Agent、GUI/Browser 自动化或完整游戏运行时。只有实际失败暴露出明确需求时才增加模块。

## 验证顺序与完成条件

| 步骤 | 交付与条件 |
| --- | --- |
| 离线功能闭环 | 正常完成、非法行动、跨轮承诺的回放；脚本策略只验证环境机制，不能充作基座结果 |
| 基座运行与规则评测 | 接入显式配置的本地模型；报告任务完成、工具调用成功、非法状态转换、承诺保持的原始计数与失败轨迹；区分模型决策错误与环境拒绝后的安全状态 |
| 最小消融 | 同一任务集合比较有/无事件记忆或状态约束，每次只改一个因素；开发任务只支持开发诊断，不作为独立泛化证据 |
| 单步动作 GRPO | 检查点由环境枚举并冻结；奖励与失败处理可用；用桩裁判跑通采样→评分→更新，再换真实裁判出结果 |
| 结果整理 | 报告训练前后开发检查点上的实际动作与执行结果、失败及实际成本；不据单次开发运行声称能力改善 |

离线闭环与套件生成只依赖标准库，可立即运行。真实 GRPO 需要本地模型目录与 GPU；`--judge-backend stub` 可在无 API 的情况下验证整条链路。整段多轮轨迹 GRPO 不在当前范围。

## 数据与证据

训练数据来自任务环境自身：`scripts/build_agent_suite.py` 在真实环境上 BFS 枚举可达的非终止状态，按可见观测签名去重，每个检查点是可回放的合法动作前缀加一个在该状态可执行的参照动作。这样检查点不可能编码不可达状态，也不需要人工构造情境池。契约细节见 [GRPO 接入说明](GRPO_LOCAL.md)。

参照动作是成对比较的基线，不是金标准：策略可以被判得比参照更好。参照、评分和分组信息不进入策略提示，策略只看从 prefix 重建的可见观察。

检查点数不代表独立情境数。评测检查点与训练检查点同属一个原创任务族，只能作为开发集；正式泛化比较需要独立来源分组和未参与开发的留出，不因演示缩小而取消隔离要求。设计任务的变体也须按任务来源分组，不把改名或换数值当作独立情境。

## 评测与奖励

任务完成和工具执行首先按环境事实检查；角色一致性、情境与历史一致性、行动合理性、对话质量沿用已有四维协议。规则正确不等于角色表现可靠，训练更新成功也不等于效果改善。

裁判协议 `judge-v0.3` 严格校验四维状态与分数、证据引用范围、胜负必须给出成对证据引用。每个样本做 AB/BA 两次调用，顺序换位后判决不一致即视为顺序伪影并拒绝。解析检查不能证明引用真正支持理由；这需要人工复核。

真实调用记录模型版本、提示、生成设置、原始响应、失败和成本。裁判与人工判断的一致率尚未测量，`manifest.json` 中据实记为 `uncalibrated`；示例配置不等于校准通过。需要可靠性结论时再补本任务的人工标注与一致率测量。

奖励组合见 [GRPO 接入说明](GRPO_LOCAL.md)。证据不足、同分和技术失败分别处理，不把缺失或失败补成零奖励。训练收益需在相同评测条件下比较；不以相同步数代表等成本，也不以同一裁判涨分代表全面能力提升。

## 复用现有实现

复用 TRL 0.26.2 `GRPOTrainer` + PEFT 0.18.0 LoRA，不重写训练框架：采样、分组优势、KL、反向传播和优化器由 TRL 负责，项目只实现任务数据、环境执行和裁判奖励适配。

V100 compute capability 7.0 不原生支持 BF16，因此用 FP16 基座 + FP32 LoRA 训练参数；`--precision auto` 也据此选择，不依赖可能包含模拟支持的 `is_bf16_supported()`。分布式用 torchrun/accelerate `PartialState`，奖励跨 rank 用 `all_gather_object` 同步后统一判定可用性。显存、吞吐和有效奖励率仍需集群实测。

## 工作边界

- 当前离线阶段不调用外部 API、不上传、不租 GPU、不下载大模型、不启动正式训练；后续外部资源需另行明确授权。
- 保留原始缓存、旧快照、请求、结果与失败记录；新运行使用新目录。data/raw/、runs/、model_cache/ 保持 Git 忽略；不自动提交、推送或创建远程，不修改工作区外项目。
- 数据按来源许可管理；设计测试环境、软件机制验证、真实模型表现和人工标注分别报告。
- 只为实际实现变化做相应验证；不重复无关训练测试。每轮更新 PROGRESS，当前路线只在本文件维护。
